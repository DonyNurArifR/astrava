## 2. In-Depth Technical Risk Analysis

### R-01: macOS Docker Desktop VirtioFS I/O Latency
- **Mechanism:** On macOS, Docker Desktop operates inside a lightweight Linux hypervisor VM. Bind-mounting host directories across the macOS-to-VM VirtioFS boundary incurs significant latency overhead on file-intensive operations (e.g., recursive AST scans, `pytest` discovery, `git status`, and `npm` package resolution).
- **Failure Mode:** Task execution times double or triple compared to bare-metal host execution; operations exceed timeout deadlines (`BudgetGovernor.expires_at`).
- **Mitigation Strategy:** Perform all active file modifications on memory-backed in-container `tmpfs` mounts or inside named Docker volumes residing wholly within the VM filesystem. Deliver source trees and retrieve deliverables via memory-streamed tar archives (`docker cp` or stdin/stdout tar piping) rather than live host bind mounts.
- **Owner Milestone:** M1.5-1 (WorkerRuntime Spike).
- **Verification Evidence:** Execute benchmark comparing 2,000 file read/write operations between a VirtioFS bind mount and a container tmpfs; enforce latency threshold $\le 1.25\times$ native.

### R-02: Host-Container UID/GID Permission Mismatch
- **Mechanism:** Containers run as an unprivileged non-root user (`uid 10001:10001`) to prevent privilege escalation. However, files mounted from macOS typically carry host UID 501. The container process cannot write to these files without loose permissions (`chmod 777`), and files generated by the container cannot be cleaned up or read by the host user without `sudo`.
- **Failure Mode:** `EACCES (Permission denied)` when agent attempts to write deliverables, or leftover container artifacts on host that cannot be removed by subsequent workflow executions.
- **Mitigation Strategy:** Control plane owns the file transport boundary. The control plane creates the snapshot archive with sanitized permissions, injects it into the container, and on task completion streams back the result as an unprivileged tar stream, unpacking files with the host operator's authentic UID/GID.
- **Owner Milestone:** M1.5-1.
- **Verification Evidence:** Run non-root worker container generating deliverables; verify host control plane reads, registers, and deletes artifacts without permission errors.

### R-03: Standalone Snapshot Clone Overhead vs Lineage Tracking
- **Mechanism:** Isolating workers requires decoupling from the host `.git` to prevent repo tampering. However, running a full `git clone` for every individual task attempt introduces massive storage amplification and several seconds of initialization latency per task in large repositories.
- **Failure Mode:** Disk space bloat and pipeline slowdown across multi-stage DAGs.
- **Mitigation Strategy:** Maintain a local reference cache on the control plane and initialize snapshots using `git clone --reference <cache> --dissociate --depth 1`. Changes are committed inside the ephemeral sandbox and exported back to the control plane as a patch bundle or fetched via `git fetch` with `core.hooksPath=/dev/null`.
- **Owner Milestone:** M1.5-2 (Isolated Workspace Manager).
- **Verification Evidence:** Measure snapshot initialization time for a 100MB repository; assert setup completes in $< 1.5$ seconds and verify host `.git` refs are unchanged.

### R-04: Unpinned Claude CLI Headless Permission Posture
- **Mechanism:** The Claude Code CLI (installed version 2.1.319) running non-interactively in print mode (`-p`) may exhibit unpinned tool permissions. In headless mode, the CLI might automatically approve file edits or shell commands that violate task constraints if prompted or hallucinating.
- **Failure Mode:** Prompt-injected task instructions cause CLI to execute unintended commands or corrupt sandbox state.
- **Mitigation Strategy:** Explicitly parameterize CLI invocations via `WorkerRuntime`: enforce strict `--permission-mode` flags or explicit `--allowedTools` / `--disallowedTools` declarations. Couple CLI invocations with OS-level sandbox constraints (`--cap-drop ALL`, read-only rootfs) so disallowed actions are blocked by the OS kernel regardless of CLI decisions.
- **Owner Milestone:** M1.5-2.
- **Verification Evidence:** Inject adversarial prompt instructing CLI to delete `/` or execute network probes; assert OS capability drops reject the operation.

### R-05: Billing & Token Quota Depletion via Injected API Credentials
- **Mechanism:** Injecting static `ANTHROPIC_API_KEY` into worker containers gives any process inside the container direct access to the operator's API quota. A prompt injection or malicious dependency could loop continuously, query expensive models, or exfiltrate the key.
- **Failure Mode:** Catastrophic financial cost or account quota exhaustion from runaway loops or credential theft.
- **Mitigation Strategy:** Workers never receive static API keys. All outbound LLM traffic routes through a Control Plane Egress Proxy. The proxy verifies the request against the active execution's `BudgetGovernor` token and cost reservations, attaches the provider authentication token at the proxy layer, and terminates the connection immediately when budget limits are reached.
- **Owner Milestone:** M1.5-3 (Egress Governance & Proxy).
- **Verification Evidence:** Configure test budget limit; execute agent task attempting token consumption exceeding the limit; verify proxy rejects request and halts container.

### R-06: Image Supply Chain Bloat & Drift
- **Mechanism:** Packaging all required development toolchains (Python, Node.js, Go, Rust, Git) into a monolithic worker image creates massive image layers ($> 8$ GB), causing slow downloads and a broad CVE attack surface.
- **Failure Mode:** Slow worker startup, image storage exhaustion, and exposure to unpatched container vulnerabilities.
- **Mitigation Strategy:** Build a minimal base runner image ($< 1.2$ GB) containing only the execution supervisor, Git, and Node.js for the Claude CLI. Pin base images by cryptographic digest (`sha256:...`). Provide language toolchains via modular, layered images or pre-warmed volume caches.
- **Owner Milestone:** M1.5-1.
- **Verification Evidence:** Automated CI pipeline scans base image via Trivy; fails on any HIGH or CRITICAL severity CVE.

### R-07: Zombie Container Lease Recovery Races
- **Mechanism:** If the host API server crashes or receives `SIGKILL`, active containerized workers continue running in Docker. Upon API restart, resumed execution pipelines could race against still-running zombie containers attempting to reconcile results.
- **Failure Mode:** Double reconciliation, inconsistent deliverable state, or fencing token collision.
- **Mitigation Strategy:** Leverage existing `BudgetGovernor` atomic reservations. On control plane startup, a container reconciliation sweep identifies all running `astrava-worker-*` containers, checks their `lease_id` against the database, issues `docker stop -t 5` to any container whose lease has expired or been revoked, and invalidates older fencing tokens.
- **Owner Milestone:** M1.5-4 (Orchestrator Integration & Crash Resilience).
- **Verification Evidence:** Simulate API hard kill during active container execution; restart API server and verify zombie container is reaped before resumption begins.

### R-08: Container & Temp Volume Inode/Disk Exhaustion
- **Mechanism:** Multiple task attempts running parallel builds, creating virtual environments, and generating artifacts accumulate stopped containers and dangling tmpfs/volume storage on the Docker host.
- **Failure Mode:** Host or Docker VM encounters `ENOSPC` (No space left on device) or inode exhaustion, preventing subsequent executions.
- **Mitigation Strategy:** Launch worker containers with `--rm` or register them in a control plane supervisor `finally` block that guarantees `docker rm -f`. Enforce storage quotas (note: `--storage-opt size=` requires overlay2 on xfs with project quotas and is **UNVERIFIED** on Docker Desktop; use size-limited tmpfs or volumes and measure) and run periodic prune tasks for orphaned volumes.
- **Owner Milestone:** M1.5-4.
- **Verification Evidence:** Execute 50 consecutive task cycles; verify Docker system disk usage returns to baseline after workflow completion.

### R-09: Pre-Existing Defect: Worktree Merge Ignores Target Branch
- **Location:** `backend/app/workspace/worktree_manager.py:276`
- **Mechanism:** `merge_worktree(repo_path, branch_name, target_branch="main")` accepts `target_branch`, but executes `git merge --no-ff branch_name` directly in `repo_p` without switching to or verifying `target_branch`. If `repo_p` is on a feature branch, the merge occurs into that active branch.
- **Failure Mode:** Worktree deliverable is merged into an unintended branch (e.g. `feat/v1.4` instead of `main`), causing silent commit misplacement or merge conflict corruption.
- **Mitigation Strategy:** Fail closed: verify the host repo's HEAD is `target_branch` and the working tree is clean, otherwise return an error. Do **not** run `git checkout` in the operator's working repo (it can clobber uncommitted work). Preferred alternative: perform the merge in a temporary dedicated worktree on `target_branch`, then fast-forward or update the ref.
- **Owner Milestone:** M1.5-1.
- **Verification Evidence:** Unit test creating a repository with two branches; call `merge_worktree` while checked out on a secondary branch; assert merge commits into `target_branch` accurately.

### R-10: Pre-Existing Defect: Flawed Path Traversal Prefix Check
- **Location:** `backend/app/services/artifact_service.py:18`
- **Mechanism:** `not str(target_path).startswith(str(base_dir))` performs string prefix matching. A path like `/storage/artifacts_evil/file.txt` matches prefix `/storage/artifacts`, bypassing traversal protection.
- **Failure Mode:** An agent or worker container can register and retrieve artifacts outside the project artifact root into adjacent sibling directories.
- **Mitigation Strategy:** Replace the string prefix comparison with `target_path.is_relative_to(base_dir)` (the project requires Python >= 3.12).
- **Owner Milestone:** M1.5-1.
- **Verification Evidence:** Unit test passing `../artifacts_evil/payload.txt` to `ArtifactService.sanitize_path`; assert `ValueError("Path traversal detected")` is raised.

### R-11: Pre-Existing Defect: Fail-Open on Worktree Failure
- **Location:** `backend/app/orchestrator/runner.py:121`
- **Mechanism:** When `GitWorktreeManager.create_worktree()` raises an exception, the error is caught and logged as a warning (`logger.warning`), and execution proceeds in the unisolated `project_work_dir`.
- **Failure Mode:** If sandbox setup fails, execution silently degrades to host-level execution without operator notice.
- **Mitigation Strategy:** Enforce fail-closed semantics. Worktree or container initialization failures must raise `ExecutionSetupError` and immediately transition execution to `FAILED`.
- **Owner Milestone:** M1.5-1.
- **Verification Evidence:** Unit test mocking worktree creation failure; assert execution halts immediately with `ExecutionSetupError` and status `FAILED`.

### R-12: Egress Proxy TLS Inspection & Certificate Tampering
- **Mechanism:** Restricting egress to `api.anthropic.com` via an HTTP proxy requires terminating TLS or inspecting SNI. If TLS is terminated, a custom CA certificate must be installed inside the worker container trust store, exposing it to potential tampering by code executed inside the container.
- **Failure Mode:** Container fails to connect to Anthropic API due to certificate validation errors, or untrusted code bypasses the proxy via SNI spoofing.
- **Mitigation Strategy:** Use forward proxy with SNI-based domain allowlisting (`CONNECT` method filtering without TLS termination) for API traffic. For environments requiring deep packet inspection, mount the custom CA certificate read-only from the control plane and lock the container's `/etc/ssl/certs` directory.
- **Owner Milestone:** M1.5-3.
- **Verification Evidence:** Attempt outbound HTTPS connection to unauthorized domain; verify proxy drops TCP connection during TLS handshake.

## 5. Orchestrator Review Notes (Sonnet)

- **R-05/R-12 are coupled and unresolved.** A credential-injecting gateway and an SNI-only allowlist are different designs; see Threat Model section 8, item 2. Both depend on Open Decision D1.
- **R-01 mitigation vs R-03.** Moving workdirs to tmpfs/volumes changes the snapshot design (stream in/out instead of mounting a host directory). It is the right direction for isolation on macOS but must be proven by the M1 benchmark; the "<= 1.25x native" target is a proposal, not a measurement.
- **Add R-13: Docker unavailable or misconfigured on the operator host.** Mitigation: fail closed (D4), spike in M1, `docker info` preflight in the API health check.
- **Add R-14: Host-side verification and `RepoScanner` still open malicious repos on the host** until moved into workers (Assessment G2; Threat Model section 8, item 6).
- **Add R-15: Model availability.** `claude-haiku-5-5` availability is unverified; a failed or substituted model silently changes cost and behavior. No substitution allowed; one authorized check required (D5).

### New risks added by this audit
- **R-16: Unauthenticated execution and configuration control.** Anyone who can reach the API can start agent executions (`/orchestrator/execute`), change which host path a project points at, edit agent configuration, and trigger model calls (`/plan`, `/understand`). Impact grows sharply once the API process can launch containers. Mitigation: M1.5-1a; the gate matrix forbids M1.5-2 before it.
- **R-17: DNS rebinding against the loopback dev server.** With no key, a hostile web page could reach `localhost:8000`. Mitigation: request-time `Host`/client-address guard in M1.5-1a.
- **R-18: Control-plane process holds Docker daemon access.** Compromise of the API process becomes compromise of every container and the Docker VM. Mitigation: authentication first, no docker socket in workers, narrow `WorkerRuntime` surface, launch-spec validator.
- **R-19: Subscription token as a worker credential.** A prompt-injected agent can read the token in its environment; the token is long-lived and revocation behaviour is unverified; automated use may be restricted by Anthropic's terms (unverified). Mitigation and fallback options: Target Architecture section 11, D1.
